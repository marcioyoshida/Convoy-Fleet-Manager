# ADR 0024: A device is installed by Terraform; the shell plans it, and the platform's runner applies it

**Status:** Draft · 2026-11-12
**Supersedes / relates to:** open finding L27.1 (Terraform state, plans and cross-provider translation have no place in the shell); the position in docs/debate-review.md §holds that day-0 infrastructure is Terraform's job outside Convoy, which this record keeps for the engine and reverses for the interface; ADR 0011 decisions 1, 2, 7, 8 and 9 and amendments 1 and 4 (devices, `by-id`, `/sys`, hotplug, classes, drivers from packages, `disconnected`); ADR 0010 and its amendment 1 (packages, platform defaults, intent); ADR 0013 decisions 1, 3 and 8 (the closed verb set, `explain`, the device family); ADR 0014 (the model proposes); ADR 0016 decisions 3 and 5 (groups own, `svc:<group>`); ADR 0017 (approvals); ADR 0006 (detach is not destroy, holds); ADR 0007 amendment 2 (secret sinks); US-27 findings L27.2, L27.3, L27.4 and L27.17

## Context

Every abstraction in this design is a device: clusters (`/dev/k8s`), object stores and artifact stores (`/dev/obj`), volumes, accelerators, queues (ADR 0012), tables and catalogs (ADR 0015), models (ADR 0014), source repositories (ADR 0011 amendment 2), telemetry stores (ADR 0023). The design says how a device is named, mounted, opened, priced and used, and that its driver comes from a package. It never says how a device comes to exist. Today the answer is "someone ran Terraform", and the shell discovers the result through the inventory.

US-27 moved production from AWS to Google Cloud and found that the move is mostly the part the shell cannot see: the VPC, the managed database, the broker, the IAM roles, the DNS zone and the keys, all held in Terraform state that no device reads. Translating that state resource by resource between providers is not possible in general: Aurora and AlloyDB, MSK and Google's managed Kafka, IAM roles and service accounts have no one-to-one mapping. What does map is the abstraction. A Kafka queue device with six partitions, 30-day retention, residency `us` and the `orders` group as owner means the same thing on either provider; only the resources that realise it differ.

Facts that constrain the design:

- Terraform (or OpenTofu) is already how platform teams create infrastructure, with state backends, module registries, plan review in pull requests, and runners (Atlantis, Terraform Cloud, Spacelift, CI) that hold the cloud credentials and the apply. A shell that calls cloud APIs to create resources would be a second, unreviewed path, and the next `terraform apply` would fight it.
- A plan is the only honest preview of an apply, and it is computed by the provider plugins against the real account. The shell's `explain` cannot predict what a plan will contain.
- State holds secret values in clear (L27.2) and resources drift from it.
- Day-2 workloads (units, Jobs, pipelines) change by the minute and are reconciled by GitOps inside clusters (ADR 0010 amendment 1). Terraform is the wrong tool for them, and nothing here moves them into it.

## Decision

1. **Installing a device is a phase, and Terraform is its engine.** A device has two phases. *Install* creates and changes the infrastructure the device stands on: a cluster, a bucket, a broker, a catalog, a vault, a telemetry store. *Use* is everything else in this design: `mount`, the verbs, the pipelines, the units. Install runs through Terraform or OpenTofu, applied by the platform's runner; Convoy never creates infrastructure with its own API calls, and never runs an apply from a session. Use is unchanged.

2. **A device package carries a module per provider, behind one contract.** A device package (ADR 0010; the driver of ADR 0011 amendment 1) now carries, beside its driver, a *device contract* and one Terraform module per provider it supports. The contract is the abstraction's inputs and outputs, written once for the class: for a queue, partitions, retention, compaction, residency, owning group, encryption and size class; for an object store, versioning, lock, lifecycle and residency; for a cluster, version, node pools by class, zones and `caps` wanted. Each module (`kafka/aws-msk`, `kafka/gcp-managed-kafka`, `kafka/strimzi`) takes the contract's inputs and must produce the contract's outputs: the device's `by-id` key, its endpoints, the identity bindings for the owning group's service identity (ADR 0016 decision 5), its price shape and the `caps` it provides. A module that cannot provide an input says so in the package manifest (`unsupported: compaction`), and `explain` prints it.

3. **`mknod` installs a device, as intent.** `mknod /dev/<class>/<name> <package>[:<provider>] [--var <key>=<value>…] [--residency=<r>] [--owner=<group>]` is a native verb in the device family (ADR 0013 decision 8; amending decision 1's list). It writes a module instance with the contract's inputs into the platform's IaC repository as a pull request (`iac_repo`, a platform default), and waits for the runner's plan and apply. Nothing is created by the session.

   ```
   mknod /dev/queue/orders-events kafka:gcp-managed-kafka \
         --var partitions=6 --var retention=30d --residency=us --owner=orders
   ```

4. **`explain mknod` is the runner's plan.** `explain` of `mknod`, and of any change below, opens the pull request as a draft, waits for the runner's `terraform plan`, and prints it in the device's terms: the resources to add, change and destroy, the contract inputs each one realises, the price band from the plan's resources and the provider's price file (ADR 0010), the identity bindings, the `caps` the device will report, and any input the module does not support. The plan's hash is what an approval pins (ADR 0017): a `mknod` in a mount or residency the platform gates creates an approval object with the plan, and the apply runs only for that hash. A plan that destroys or replaces a resource holding data is refused unless `--with-data` is given, and never while a hold covers the data (ADR 0006).

5. **Applying registers the device.** When the runner applies, the module's outputs register the device in the inventory: the `by-id` key, `/sys/<class>/<id>/` with its metadata, price and `caps`, and a device-added hotplug event (ADR 0011 decision 8). The device records the module instance that installed it at `/sys/<class>/<id>/iac/` (repository, path, module and version, state address, last apply). `mknod` returns when the device is registered and reachable, with a receipt naming the commit, the plan hash and the apply.

6. **A device changes by its contract, and removal is destroy with the usual guards.** `/sys/<class>/<id>/iac/vars/` holds the contract inputs as files; writing one (`echo 12 > /sys/queue/<id>/iac/vars/partitions`) is a change to the module instance through the same pull request, plan and apply, with `explain` printing the plan first. `rm --with-data /dev/<class>/by-id/<id>` destroys the device through the module (ADR 0006: never while a hold covers it, never without `--with-data` where it holds data, listing what is retained elsewhere); `umount` only detaches it from the session. A write to a resource that a module instance owns but that is not a contract input (a bucket policy, a topic's config) is written as intent to that instance or refused under `iac=refuse` (finding L27.4, ADR 0010 amendment 1).

7. **State is a device, read under the scrub.** Each state backend the platform names is a device under `/dev/iac/by-id/<backend>`; `ls` lists module instances and resources by address, `ls -l` shows dependencies, provider and the device each resource realises, and `stat` a resource's attributes. Reads pass the artifact scrub and withhold attributes the provider marks sensitive (L27.2); the device is readable by the platform group and by owning groups for their own instances. The runner's drift detection appears as `iac: drifted` on the device in `ls -l /dev/<class>/` with the differing attributes, and the account inventory comparison of L27.3 lists resources that no state holds.

8. **A device not installed by a module is still a device, and says so.** Clusters, stores and brokers that predate this record, or that another team runs, are registered as today, with `iac: none` in `/sys/<class>/<id>/iac/`; every verb works on them, and `mknod --adopt /dev/<class>/by-id/<id> <package>:<provider>` writes a module instance with Terraform `import` blocks for the existing resources, so the next plan shows no changes and the device becomes `iac: managed`. The platform may set `iac=required` per class, after which `mount` of an `iac: none` device warns and `mknod` is the only way to add one.

9. **Moving a device to another provider is a new instance of the same contract.** `mknod /dev/<class>/<name> <package>:<other-provider> --like=/dev/<class>/by-id/<id>` instantiates the other provider's module with the source device's contract inputs, and `explain` prints the plan beside the inputs the target module does not support. This is how US-27's queue, object store, catalog, vault, telemetry store and cluster move: by contract, not by translating resources. Data is moved afterwards with the verbs of use (`cp`, `backup`, the replication units of rule L27.7), never by Terraform. Resources outside any device module (a legacy repository's raw `aws_*` resources) can be translated only as a proposal: the assisted shell (ADR 0014) proposes module instances or resources for the target, a person reviews the diff, the resources with no counterpart are listed, and the target plan is the proof; the model never applies.

10. **The runner is the platform's, and so are its credentials.** The apply runs in the platform's runner under its identity (`svc:platform`, or a group's runner identity where the platform delegates a module path to a group); the session holds no cloud credential that can create infrastructure. `caps: iac:<runner>` names the runner and how Convoy reads its plans and applies (Atlantis comments, the Terraform Cloud API, a CI status); without it `mknod` is refused, naming the capability. The runner's policy checks (OPA, Sentinel) run as they do today, and a policy failure is exit 3 with the rule.

## Declined

| Proposal | Why not | What replaces it |
|---|---|---|
| the shell creating infrastructure through cloud APIs | an unreviewed second path; the next apply fights it; credentials in the session | `mknod` writes a module instance; the runner applies (decisions 3, 10) |
| running `terraform apply` from the session | the session would hold infrastructure credentials, and an apply outside the runner skips its locks and policies | the platform's runner (decision 10) |
| translating HCL resource by resource between providers as the main path | no one-to-one mapping between managed services; results that look complete and are not | instances of the same contract per provider (decision 9); resource translation only as a reviewed proposal |
| Terraform for units, Jobs and pipelines | changes by the minute, reconciled inside clusters | GitOps intent (ADR 0010 amendment 1), unchanged |
| a second engine (Crossplane, Config Connector, ACK) beside Terraform now | two state models for one device; two places to look for drift | Terraform or OpenTofu; another engine under the same contract is an open item |
| `explain` predicting the plan from the module's source | only the provider plugins against the real account know what a plan contains | the runner's plan is the `explain` (decision 4) |

## Consequences

- L27.1 is drafted here. ADR 0013 decision 1 gains `mknod` in the device family, with `--adopt` and `--like`, which a later revision of decisions 1 and 8 carries; `/sys/<class>/<id>/iac/` and `/dev/iac/` are new paths. The position of debate-review §holds stands for the engine (Terraform installs infrastructure) and is reversed for the interface (the shell plans, installs, changes and reads it).
- Packages change shape: a device package carries a driver, a device contract and modules per provider (ADR 0010, ADR 0011 amendment 1). The command map and US-27's findings L27.2 (state is a sink), L27.3 (inventory comparison), L27.4 (writes to managed resources as intent) and L27.17 (DNS weights as intent) are realised by decisions 6 and 7 and were applied with US-27 on 2026-11-12 (L27.2 in ADR 0007, L27.3 in ADR 0011, L27.4 in ADR 0010 amendment 1, L27.17 in ADR 0019).
- New `caps` keys: `iac:<runner>` (`atlantis`, `tfc`, `spacelift`, `ci`). New platform defaults: `iac_repo`, `iac=required|optional|refuse` per class, the state backends, the runner identity per module path. New package fields: `contract`, `modules` per provider, `unsupported` per module.
- ROADMAP: the contract and modules in device packages are M9 with packages; `mknod`, the plan as `explain`, registration from outputs and `/sys/<class>/<id>/iac/` are M8 with the fleet inventory; the state device and drift are M5 with mounts; adoption with `import` blocks is M8; approvals on plan hashes are M7.
- Open, to be settled against this ADR: a second engine under the same contract (Crossplane, Config Connector); module versions and how a contract evolves without forcing every instance to re-plan; device installs that span providers (a cross-cloud interconnect); cost of plan runs on large states; who owns a module path when a group installs its own devices. [US-28](../user-stories/US-28-install-my-own-devices.md) probes this record under the data engineer persona with a delegated module path; it proposes revisions to decisions 2, 4 and 9 (L28.12, L28.1, L28.14), eleven rules and one accepted limitation (L28.15, a clean plan is not a clean apply), not yet applied.
