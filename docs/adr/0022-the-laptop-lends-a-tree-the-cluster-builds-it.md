# ADR 0022: The laptop lends its working tree; the cluster builds, runs and debugs it

**Status:** Draft · 2026-11-11 · revised 2026-11-11 with user-story findings L25.1, L25.4, L25.7 and L25.11 (decisions 1, 2, 4, 5 and 6, marked inline) and rule L25.10 (decision 3)
**Supersedes / relates to:** open finding L24.1 (the laptop's working tree and local images have no path into the session); ADR 0005 (the laptop is a terminal); ADR 0020 decisions 2, 5 and 8 (the journal, the attach protocol and its channels, hosts per residency); ADR 0011 amendment 2 (source repositories are devices) and amendment 4 (`disconnected`); ADR 0001 (artifact ids from content); ADR 0003 and rule L24.5 (local stages run in the source mount's image); ADR 0007 amendment 2 (the artifact store is a secret sink, the put-time scrub); ADR 0013 decisions 3, 4 and 7 with L24.3 and L24.4 (unit env is a declaration, `explain --at`, the release diff) and rules L24.2, L24.8 and L24.9 (platforms, branch units, provenance); ADR 0019 decisions 4 and 7 (egress, the hosts view and `attach -L`); ADR 0016 decisions 3 and 5 (objects belong to groups; processes run as `svc:<group>`); US-24 (the developer persona)

## Context

US-24 took a service from a green laptop to production and found that the design has no inner loop. The laptop is a terminal (ADR 0005), so the files a developer is editing are nowhere the session can read; the only route was pushing unfinished code to a shared branch. An image built on the laptop is the wrong architecture for the cluster, carries whatever `COPY . .` picked up, and has no provenance. The developer's tools (the editor, the debugger, the language server) stay on the laptop, and the code they debug has to run where its dependencies, its network policy and its profile are, which is the cluster.

Facts that constrain the design:

- A developer saves a file many times a minute. Anything that turns each save into a commit, a push and a CI run is too slow to be used, and will be bypassed with `kubectl` and a laptop image.
- A laptop sleeps, changes networks and goes offline. A stage that reads the laptop's disk live across the WAN fails when the lid closes, and every read is a round trip.
- Uncommitted code is still the company's code, and a working tree often holds things that must not leave the laptop: `.env` files, cloud credentials, a database dump for a test.
- The attach protocol (ADR 0020 decision 5) is already one authenticated WebSocket from the client to the session through the platform's gateway, with channels; it is the only path from the laptop into the platform.
- Images that reach production come from CI (rule L24.9). Images for the inner loop must be fast to build, built for the cluster's architecture, and still say where they came from.
- A debugger needs a port on the process it debugs and patience from the liveness probe. A port-forward from the laptop to a unit the user's group owns already exists (ADR 0019 decision 7).
- Nothing in the cluster may call into the laptop (L24.11): the laptop is not on the platform's network and is not trusted to serve a shared environment.

## Decision

1. **The laptop lends a directory, or chosen paths of one root; the session receives complete snapshots.** `convoy attach --lend=<dir>[:<name>]` (or `lend <dir>` from the client while attached) declares a directory on the laptop; `lend <root> --only=<path>…`, or the paths a repository's `.convoylend` declares per service, lends a sparse set of paths of one root as one tree, so a service in a monorepo and the libraries its build copies travel together without the rest of the repository (revised 2026-11-11, L25.1). The client sends it to the session over a lend channel of the attach protocol as content-addressed snapshots: the first send is the tree, each later one only the changed files, debounced after saves. A snapshot becomes current only when every file in its manifest, less the withheld ones, is in the artifact store; an interrupted snapshot is discarded and the device stays on the last complete tree, so a laptop that sleeps mid-send never leaves a current tree with files missing (revised 2026-11-11, L25.4). The session sees it as a source-repository device of kind `worktree`, `/dev/scm/by-id/wt-<user>-<host>-<name>` (rule L25.10), mounted read-only at `/src/<name>`. Each snapshot has a tree id; for a git working tree the tree id is the git tree hash of the lent paths, with withheld files hashed from their content on the laptop and never sent, so a commit whose tree matches is provably the code the snapshot held (revised 2026-11-11, L25.11). A stage reads the snapshot current when it starts, `explain` prints its id and age, and `--wait-sync` waits for the client's last save to arrive. Because a snapshot is content, every artifact computed from it has an artifact id under ADR 0001, and `replay` works as long as the snapshot is retained.

2. **What leaves the laptop is filtered on the laptop.** The client applies `.gitignore`, the repository's `.convoyignore`, and always excludes `.env*`, `*.pem`, `*.key`, the cloud credential files the platform names and anything larger than the platform's `lend_file_max`. It then runs the platform's artifact scrub rule set (ADR 0007 amendment 2; the client fetches the rule version `explain` prints) over every file before sending it; a file with a match is withheld, and the session lists it under `/src/<name>` as `withheld: <rule>`, never with its content. A lend above the platform's `lend_max` is refused with the size and the largest directories. The session may name only paths in the client's manifest, so a compromised session cannot read the rest of the laptop; the request is an authorization, not a lazy fetch, because a snapshot is complete before it is current (decision 1; revised 2026-11-11, L25.4). `lend --dry-run` and `explain lend` print what would be sent, excluded and withheld, and data files are refused by the platform's `lend_exclude` (rules L25.2, L25.3).

3. **A snapshot is data at rest with a short life.** Snapshots are stored in the artifact store of the session's residency (ADR 0016 decision 11) under the retention class `worktree` (platform default `worktree_retention`, 7 days after the last use), owned by the session's primary group with the user as actor (ADR 0016 decision 3) but readable only by the lender and the builds and units the lender starts from it, unless `lend --share=<group>` widens it, which is recorded (revised 2026-11-11, rule L25.10), and priced in `df` like any artifact. When the client detaches, the device goes `disconnected` (ADR 0011 amendment 4): its last snapshot stays readable with its age, and nothing that runs from it stops. When the laptop reattaches, the client sends the difference and the device returns to `ready`.

4. **The cluster builds; the laptop does not have to.** The toolbox carries `image-build`, an executable over a rootless BuildKit with the annotation `side effect: push`, `class: build`: `run image-build /src/<name> [--file=<Dockerfile>] [--platform=<list>]` builds from a snapshot inside the session's residency, as `svc:<group>`, with its layer cache in the artifact store, and pushes to the group's development path in the platform's registry (`caps: dev-registry`). A context or a `COPY` source outside the snapshot is refused at plan time, naming the path and the lend's root (revised 2026-11-11, L25.1); the build steps hold no registry credential, and the builder pushes after the last step (rule L25.9). The platforms default to those of the pools under the cwd's mount, so the arm64 laptop and the amd64 pool of US-24 never meet (rule L24.2). The output is a digest, and the build's receipt is an attestation: `provenance: session`, the snapshot tree id, the Dockerfile and the base image digests. A `.devcontainer` definition in the snapshot is built the same way and is what `image=devcontainer` (rule L24.5) resolves to.

5. **Provenance has three levels, and the mount says which it takes.** Rule L24.9's `provenance=ci|any` becomes `provenance=ci|session|any`: `ci` takes only digests with the CI's attestation; `session` also takes digests `image-build` built from a snapshot or a branch; `any` also takes digests pushed from a laptop, which a developer may still do (`docker push` to the group's development path with the login of ADR 0016) and which carry `provenance: laptop`. The default for a test profile is `session`, for a production profile `ci`. `explain` prints the digest's provenance and the mount's requirement, and for a CI digest the snapshot that passed with the same git tree, or that none did (revised 2026-11-11, L25.11); the scrub of layers (rule L24.9) applies to every level.

6. **A dev unit runs the snapshot in the place it will run.** `run --unit <name> --from=/src/<name> [--like=<mount>] [--follow] [--debug=<port>]` builds the image from the current snapshot (decision 4) and creates a unit named `<name>-<user>` by default in the cwd's mount, with its own address: a name held by a unit not created from a lend is refused, naming the unit and its owner, no Service of another unit selects a dev unit, and callers reach it only by an explicit `--connect` (revised 2026-11-11, L25.7); a mount whose `release_path` is `git` refuses it (rule L25.12). The unit is created with its declared env (L24.3) and egress (L24.10). It is a branch unit under rule L24.8: it carries `branch_unit_ttl`, its daily cost shows in `ps`, and it ends at the TTL or with the lend. `--like=<mount>` applies the target mount's Pod Security level, read-only root, defaulted limits and egress policy to the dev unit inside the test namespace, where the test profile allows tightening (it may always tighten; it may never loosen), so the differences `explain --at` would list (L24.4) are exercised before the release rather than discovered after it.

7. **`--follow` is the hot reload, and it is confined to dev units.** With `--follow`, a new snapshot updates the unit: where the image's annotation declares `live: sync <paths> [then <command>]`, changed files under those paths are copied into the running containers and the command runs (a reload, a restart of the process); anything else triggers a rebuild and a rollout. Every update is a line in the unit's receipt with the tree id, so what was running at any moment is known. `--follow` is refused on a mount whose provenance is `ci`, and on any unit that is not a branch unit.

8. **The debugger stays on the laptop and reaches the process by the hosts view.** `--debug=<port>` starts the runtime's debug agent on that port through the image's annotation (`debug: debugpy|delve|jdwp|node-inspect <port>`), relaxes the liveness probe while a debugger is attached (the agent reports attachment; readiness is unchanged, so the unit takes no traffic while paused), and sets `--replicas=1`. The developer reaches the port with `attach -L <port>:<unit>-0:<port>` (ADR 0019 decision 7), which needs the unit to be owned by one of the user's groups, so the editor's debugger attaches as if the process were local. `--debug` is refused where the mount's profile has `debug=off`, which is the production default; rule L24.11 stands.

9. **A process on the laptop may call into test, never the reverse, and never with test's secrets.** A service run under the laptop's own debugger reaches test's units it is entitled to through `attach -L`, with the same rules as the hosts view. `attach --env-of=<unit>` writes the unit's declared non-secret variables to a file on the laptop with addresses rewritten to the forwards; variables that are secret references are listed by name and never resolved on the laptop (ADR 0007: values never reach the client). Nothing in the cluster routes traffic to the laptop: intercepting a shared unit's requests to a laptop is declined.

10. **The laptop's own loop is untouched.** `docker compose`, local tests and the editor keep working with no Convoy in them. Convoy's part of the loop starts at `lend` and adds three things the laptop cannot give: the cluster's architecture and policy (decisions 4 and 6), the test environment's real dependencies (decision 9) and the differences from production (L24.4). `explain` on any line under `/src/<name>` prints the snapshot, the image each stage runs in and the provenance of every digest, so the developer always knows which copy of their code is running where.

## Declined

| Proposal | Why not | What replaces it |
|---|---|---|
| mounting the laptop's disk live in the session (sshfs, 9P over the attach channel) | every read is a WAN round trip; a closed lid fails every stage reading it; the session could read anything the mount exposes | snapshots by request from the client's manifest (decisions 1 and 2) |
| two-way sync | the session would become a second place code is edited, with conflicts; build output belongs in artifacts | one-way lend; outputs are artifacts, fetched with `cp` through the attach channel |
| pushing work in progress to a shared branch as the only route | slow, noisy for reviewers, and it makes unfinished code look like a proposal | the lend (decision 1); branches stay for code meant to be read |
| the laptop as a backend (ADR 0005) | a sleeping laptop would stop stages and the audit stream would be client-controlled | the dev unit in the cluster (decision 6) |
| intercepting a shared unit's traffic to the laptop (Telepresence, mirrord style) | puts an untrusted machine in the request path of an environment others use (L24.11) | the dev unit with `--debug` (decision 8) |
| resolving test secrets onto the laptop for a local run | values never reach the client (ADR 0007) | names only; the process that needs the value runs in the cluster |
| building images on the laptop by default | wrong architecture, layers holding local files, no provenance | `image-build` from a snapshot (decision 4); laptop pushes stay possible as `provenance: laptop` |
| `--follow` on any unit | a live-updated unit is not a release | dev units only, never on `provenance=ci` (decision 7) |

## Consequences

- L24.1 is drafted here. The lend channel is a new channel of the attach protocol (ADR 0020 decision 5); the `worktree` kind is a new source-repository device kind (ADR 0011 amendment 2); `image-build` is an executable in the toolbox, not a verb, so ADR 0013 decision 1 is unchanged, while `run --unit` gains `--from`, `--like`, `--follow` and `--debug` and `attach` gains `--lend` and `--env-of` (ADR 0013 decision 11 requires them in the flag tables, which a later revision of decision 4 carries).
- Rule L24.9 gains the `session` level (decision 5). New `caps` keys: `dev-registry`, `image-build`. New platform defaults: `lend_max`, `lend_file_max`, `lend_exclude` and `lend_data`, `worktree_retention`, `provenance` per profile with `session` for test, `debug` and `debug_pause_max` per profile, `follow_rebuild_max`, `build_egress`, `dev_mounts`, the credential file list the client excludes. New annotation fields: `live:` and `debug:` on images.
- ROADMAP: the lend channel, the client's filter and the `worktree` device are M2 with the attach protocol and M5 with mounts; `image-build`, its cache and the attestation are M3 and M4; dev units with `--like`, `--follow` and `--debug` are M11 with units; provenance levels are M7.
- The developer's loop costs storage for snapshots and build cache, compute for builds and the dev unit's hours, all priced to the group and shown by `df`, `cost` and `ps`.
- [US-25](../user-stories/US-25-edit-here-run-there.md) probes this record under the developer persona with a monorepo and a shared test namespace. Its four amendments were applied inline on 2026-11-11: L25.1 (sparse lends of one root, a build context outside the snapshot refused, decisions 1 and 4), L25.4 (a snapshot is current only when complete, decisions 1 and 2), L25.7 (dev units named `<name>-<user>` with their own address, decision 6) and L25.11 (the tree id is the git tree hash; a CI digest names the snapshot that passed, decisions 1 and 5). Its eleven rules are written below, with cross-references in ADRs 0003, 0010, 0011, 0013 and 0019, the command map and ROADMAP M2, M3, M5 and M11. L25.16, the save-to-reload latency, is accepted: no target, the measured time is printed.
- Settled by US-25: monorepos are lent as sparse paths of one root (L25.1); a snapshot is promoted by committing on the laptop, never in the session, and the git tree hash ties the commit to the snapshot (L25.11); the reload latency is measured, not promised (L25.16). Still open: large binary assets in a working tree.


Note · 2026-11-13: the draft [ADR 0026](0026-a-registry-is-a-device-a-tag-is-a-name-for-a-digest.md) makes the registry `image-build` pushes to a device; `caps: dev-registry` names the path `/registries/<id>/dev/<group>/`, and every tag a build or a release names is resolved to a digest at plan time (decision 4).
## Rules · 2026-11-11 · from the user-story probes

Each line is a `rule` finding from `docs/user-stories/README.md` written here as decided; the story holds the reasoning.

- **L25.2** (US-25) `explain lend <dir>` and `lend --dry-run` print what the client would send, exclude and withhold, with sizes and the rule or ignore file for each; `image-build` lists the excluded and withheld files under its context and refuses when a `COPY` or `ADD` needs one; `.convoyignore` may re-include a git-ignored path (`!gen/`), which is still scrubbed.
- **L25.3** (US-25) the platform default `lend_exclude` names data patterns (`*.sql`, `*.dump`, `*.parquet`, `*.sqlite`, `*.csv` above a size) that the client refuses, naming the file, the pattern and the session's residency; `--with-data` overrides only where the profile sets `lend_data=allow`; the lend's receipt lists the data files sent.
- **L25.5** (US-25) a followed unit's identity is its digest and its tree; `ps` and `explain` show both and the number of updates since the build; a digest counts as passed in a mount only for the tree it was built from, so `--image=<digest>` and the release diff (rule L24.4) refuse under `--strict`, and otherwise warn, when the passing run carried live updates.
- **L25.6** (US-25) the debug agent reports pause and resume; `ps` shows the process as `paused (debugger)` with its duration; past the profile's `debug_pause_max` (default 10 minutes) the pod is restarted, with a receipt line naming the pause and the connections it held.
- **L25.8** (US-25) a followed unit has at most one build in flight, later saves coalescing into the next; past `follow_rebuild_max` builds per hour it stays on sync-only updates with a notice; `ps` shows the builds and their cost since `--follow` began; `--follow=sync` never rebuilds.
- **L25.9** (US-25) build steps run with no registry credential except a pull-only token for the base images, and with the profile's `build_egress` (package mirrors by default); the builder pushes after the last step with its own credential; the attestation records the egress used.
- **L25.10** (US-25) the worktree device id is `wt-<user>-<host>-<name>`; snapshots are readable by the lender and by the builds and units the lender starts from them, and by a group only with `lend --share=<group>`, which is recorded (decision 3).
- **L25.12** (US-25) `run --unit --from` is refused in a mount whose `release_path` is `git`, naming the reconciler and the platform's development mounts (`dev_mounts`); a development mount has `release_path=direct` and is excluded from the reconciler.
- **L25.13** (US-25) a local stage whose cwd is under a worktree mount gets a per-process writable overlay, discarded at exit; outputs meant to be kept are redirected to artifacts; `explain` prints `overlay: discarded`.
- **L25.14** (US-25) a unit's `--env NAME=<value>` whose value matches the scrub rules (ADR 0007 amendment 2) is refused at plan time, naming the variable and the rule, never the value; `attach --env-of` applies the same rules and writes no matching value.
- **L25.15** (US-25) `explain` of `--like=<mount>` lists the policies on the target that `--like` does not reproduce, by kind and name (mesh policies, admission mutations, objects outside the profile), read from `caps` and the target namespace.
- **L29.11** (US-29) a conversion to another image format starts from the OCI digest, is cached by it, and the receipt records both hashes (full rule in [ADR 0025](0025-a-computer-is-a-device-kubernetes-is-one-driver.md)).
